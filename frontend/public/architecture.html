Mirror Engine · Delta Exchange India

How the copier actually works

A master account trades. Every follower in its group gets the same trade, scaled to its own balance, within a second. A second system then checks the result every ten seconds and fixes what the first one got wrong. This is what both of them do, and the numbers they run on.

The account model

An owner holds one or more groups. A group is one master account and the followers attached to it. One owner can run several masters at once, which matters more than it sounds: most of the engine's in-memory state has to be keyed per master, not per owner, or two desks trading the same contract overwrite each other's answers.

Each account carries its own API key pair, its own status (active / paused), and its own sizing settings. A new account is created paused.

02The live copy path

What happens between the master's fill and the follower's order. This path is event-driven — no polling — and is the one that has to be fast.

1

Master's websocket delivers the event

One authenticated Delta websocket per master, subscribed to orders and positions. On connect it replays a snapshot of everything currently resting and held, so a restart doesn't lose the book.

2

The engine sizes it for each follower

The master's quantity is converted to each follower's own quantity. Section 03 covers the arithmetic. If the ratio cannot be computed, the leg is skipped rather than guessed.

3

Four risk checks run locally

Account is active; circuit breaker not tripped; quantity is positive; quantity within max_position_size. A refusal here never reaches the exchange, so there is no rejection for anyone to see — which is why a refusal now sends its own alert.

4

Idempotency guard

One Redis read answers whether this master order is already mirrored to this follower. The same resting order arrives repeatedly — on every websocket update and on every 30-second order sweep — so this guard is what stops duplicates across all paths.

5

Order goes out, mapping is written

ordermap:{master_order_id} records which follower order belongs to which master order. Everything downstream — cancels, edits, exits, reconciliation — depends on that mapping existing.

6

Confirm, then escalate if needed

After a 3-second settle the engine re-reads the fill. A mirrored limit order that still hasn't filled after 5 seconds — checked twice — is escalated to a market order, so the follower doesn't sit out a move the master is already in.

7

Protection is mirrored with a jitter

The master's SL/TP is copied to each follower, offset by 50 price units by default (~0.07% on BTC). Identical triggers would all fire in the same instant against the same book; the offset spreads them.

03Sizing: the balance ratio

Four allocation modes exist. The desk runs auto_ratio on every live group, so that is the one that matters.

# auto_ratio — the mode in production ratio = follower_balance / master_balance qty = master_quantity × ratio # JD group, as logged on 2026-11-19 22:05 UTC follower_bal = 7595.09 master_bal = 8509.61 ratio = 0.892531 master 800 lots → follower 715 lots

Two decisions worth knowing

It uses total balance, not free margin. Free margin shrinks as positions lock it up and grows as they close, so a ratio built on it swings with the book. On 2026-08-03 the same unchanged positions read "expected 22" at one moment and "expected 30" half an hour later — a 30% move that fired four false mismatch alerts. Total balance only moves when someone actually deposits or withdraws.

An unreadable balance returns zero, never 1:1. On 2026-08-02 a master's balance read as 0.0 five times in one day. A 1:1 fallback would have computed a 610-lot target for a 70 USD account. Returning zero makes the caller skip; the reconciler retries once balances read again. A missed copy is recoverable, a 100× order is not.

04The reconciler

The live path is fast and can miss things: a dropped websocket event, a rejected order, a fill that lands while the backend is restarting. The reconciler is the safety net that compares reality against intent and fixes the difference.

Two independent sweeps run per master. The order sweep every 30 seconds re-mirrors any resting limit order the follower is missing. The position sweep every 10 seconds compares held positions and applies one of four corrections per leg.

CLOSE
Master is flat on a symbol the follower still holds. Market close, reduce-only
OPEN
Master holds a leg the follower has nothing on — the live copy never landed. Only if the master's fill is < 180s old
TRIM
Right side, too much size. Cut back to the ratio target. Deadband: 5% or 1 lot, whichever is larger
TOP-UP
Right side, too little size. Buy the shortfall. Acts on the smaller of two observations

Nothing acts on a first sighting

A book read mid-flight — an order half filled, a position still settling — looks wrong for a moment and then isn't. So every correction must see the same discrepancy on two consecutive passes before acting. At a 10-second interval that puts a real correction about 20 seconds after the first sighting.

That two-pass memory is held per master. It used to be a single shared set, which worked for as long as there was only ever one active master. The moment a second came online, each master's pass overwrote the other's memory, nothing was ever confirmed twice, and nothing was ever corrected.

Per-leg isolation · added 2026-11-20

All four corrections used to sit inside one try/except per follower. Whichever leg raised first cancelled every other leg — and the OPEN sweep below it. Each leg now has its own guard, and a leg that crashes sends its own Telegram alert saying it was not corrected.

When a discrepancy won't settle

A discrepancy that is still there after 60 seconds is escalated to Telegram. Below that threshold the reconciler is still working normally and stays quiet — an alert on every pass would be a stream nobody reads. Settling clears the clock, so a later recurrence is timed from scratch rather than alerting instantly off an old one.

Failure stance

Where Redis cannot be read, the engine fails toward placing the order. A spurious order can be cancelled; a missed one is a follower that silently stops tracking its master. The one exception is sizing — an unreadable balance always skips.

07Alerting

Every alert is routed by owner, so one desk's alerts never land in another desk's group. The rule we work to: an alert fires only when a human has to do something.

Alerts name what the engine failed to do, not only what it did. That was added after four separate faults in one day were found by people staring at the exchange rather than by us — including a follower that doubled to 5,539 against a target of 2,771, detected eight seconds later, logged thirteen times across two minutes, and never mentioned anywhere.

08Where it is weak

The honest list, as of 20 November 2026.

Open · needs a decision Pause and resume has no baseline On resume the engine compares the follower against the master and treats whatever is already on the books as its own, then adjusts it. On 20 Nov 03:49 IST this trimmed 85 lots across two legs that nobody had asked it to touch. The desk needs to choose: leave pre-existing positions alone, or keep correcting the whole book.
Open · being traced A master exit that never mirrored The same incident started with four legs the master had exited and the follower still held. Why that exit never reached the follower is not yet established. Everything downstream — the unprotected positions, the trims — followed from it.
Open · on hold Escalation is a flat timer A limit that is still filling at 5s is killed anyway, and the reconciler would market the remainder 15s later regardless. Both should gate on "our order is live and still filling", with a ceiling around 30s. Held at the desk's request.
Fixed · 20 Nov An alert line that crashed the reconciler Two variables read before they were assigned took down the whole correction pass. One of them had missing-leg recovery switched off in production for two days. Both fixed, both pinned by a test that uses CPython's own flow analysis to catch the next one.
The pattern behind most of these

The engine is good at detecting that something is wrong and historically bad at telling anyone when its own correction fails. Detection and correction live in the same process, so when correction breaks, detection usually goes quiet with it. That is the thing worth designing against, more than any individual bug.
